# What did skills 1.3.2 change in the contracts the Cockpit reads or spawns?

Research for [#196 What did skills 1.3.2 change in the contracts the Cockpit reads or spawns?](https://github.com/dbarjs/hero-synergy/issues/196), a ticket of the map [#195 Specs and build tickets in the Cockpit](https://github.com/dbarjs/hero-synergy/issues/195), done on 2026-11-16.

Everything below comes from a clone of `mattpocock/skills` (tags `v1.3.1` at [24fe0ef] and `v1.3.2` at [d1478fc]; `main` at [5863806], 2026-11-12, the same commit `gh api repos/mattpocock/skills/commits/main` returned), its `CHANGELOG.md` and release list, the installed plugin copy at `~/.claude/plugins/cache/claude-plugins-official/mattpocock-skills/1.3.1/`, `~/.claude/plugins/installed_plugins.json`, `claude plugin list --json` on Claude Code 2.1.325, the manifest and pull requests of `anthropics/claude-plugins-official` read through `gh api`, `gh` 2.100.0's own help, and this repo at `3e4831f`. The method is the one of [#31 Which mattpocock-skills version does the Cockpit read?](https://github.com/dbarjs/hero-synergy/issues/31): diff the tags file by file, then walk the mattpocock-skills section of [`docs/upstream.md`](https://github.com/dbarjs/hero-synergy/blob/main/docs/upstream.md) row by row. No plugin was installed or updated, and nothing on the tracker or in this repo was written but this file.

## Answer

**Nothing the Cockpit parses changed between 1.3.1 and 1.3.2.** Every map heading, label name, claim rule, body fallback, frontmatter key, skill name and manifest entry is the same text. The manifest differs in its `version` string only, and no existing `SKILL.md` changed a single frontmatter character. The canary's own check (`packages/canary/src/cli.ts skills`), run here against trees of `v1.3.1`, `v1.3.2`, [49dd158] and the installed copy, passes on all four.

**What changed is what a session is told to write.** Four changes are the ones the map leans on, and each needs one nuance:

1. `wayfinder` forbids triage labels on a map and its tickets ([8295b8e], [skills#1181]). The same commit says the type is read from the label, never the body.
2. `to-tickets` makes each ticket a sub-issue, but only "if the source was an existing issue", and drops the `## Blocked by` section when the edges are native ([cffab50], [skills#1188]). Native blocking itself was already asked for in 1.3.1.
3. `implement` fetches a passed ticket reference and states its title ([6d6a5b9], [skills#1196]). The reference stays optional, and the skill still says nothing about claiming.
4. The GitHub template's new `gh` flags arrived in two pull requests: `--parent` and `--add-sub-issue` in [skills#1188], `--blocked-by`, `--add-blocked-by` and comment-then-close in [skills#1228] ([ed0de59]).

**This machine does not run 1.3.2, and the official marketplace cannot deliver it today.** The installed plugin reports `1.3.1` and is commit [49dd158] of 2026-10-09, which is also the marketplace's pin since 2026-10-16. It already holds changes 1 to 3 and the first half of 4. It lacks the second half of 4, the own-repo rule and the fresh-context lines. Re-running `/setup-matt-pocock-skills` here would start from the template that `docs/agents/issue-tracker.md` already equals byte for byte.

**Ahead of 1.3.2, `main` touches no contract.** It changes `implement-spec`'s prose and adds one in-progress skill, `software-factory`, whose frontmatter the Cockpit's reader cannot parse. That file is the whole of [#184 Upstream break: skills v1.3.2](https://github.com/dbarjs/hero-synergy/issues/184): it is on `main`, not in the 1.3.2 tag, and not in the plugin manifest.

**Stale in this repo:** the tracker doc is five hunks behind the 1.3.2 template; the glossary's AFK ticket entry, the README's bypass paragraph and the setting's description still let a triage label make a decision ticket AFK; and twelve places in the register carry a version, a pin or a wording the diff has overtaken. `docs/agents/triage-labels.md` is already the 1.3.2 template byte for byte.

## The four changes the map leans on

### 1. Wayfinder's label rule

- **Before** (`wayfinder/SKILL.md` at 1.3.1): "Each ticket carries a `wayfinder:<type>` label, one of `research`, `prototype`, `grilling`, `task` (see [Ticket Types](#ticket-types))."
- **After** (1.3.2, line 65): the same sentence, followed by "`wayfinder:` labels are the only labels a map and its tickets carry, never a triage label like `ready-for-agent`: they are decisions, not implementation work."
- **Commit and PR:** [8295b8e], 2026-10-07, [skills#1181], "wayfinder: no triage labels, no placeholder refs, no research PRs". The commit message gives the reason, from upstream issue [skills#518]: "Maps and tickets picked up a triage-state label (ready-for-agent), which reads as "ready to implement"".
- **Changelog:** "`wayfinder` no longer labels maps or tickets `ready-for-agent`".
- **In the installed copy:** yes.
- **Nuance for the map.** The rule covers the map issue too, not only its tickets. It is a rule for what wayfinder writes, so a map charted before the rule can still carry the label: upstream's own reason for the fix is that real sessions did it. In this repo none does: on 2026-11-16, 98 issues carry a `wayfinder:` label, 48 carry a triage label, and none carries both (`gh issue list --state all --search` with both label groups).
- **Who still applies `ready-for-agent` at 1.3.2:** `to-spec`, on the spec itself ("Apply the `ready-for-agent` triage label - no need for additional triage"); `to-tickets`, on each ticket ("unless instructed otherwise; the tickets are agent-grabbable by construction"), and as `**Status:** ready-for-agent` in the local ticket template; and `triage`. All three texts are unchanged from 1.3.1. Both specs the map names, [#37 Spec: hero-synergy v0.1.0, the Cockpit](https://github.com/dbarjs/hero-synergy/issues/37) and [#163 Read a local tracker's state in every form a real five-month tracker holds](https://github.com/dbarjs/hero-synergy/issues/163), carry `ready-for-agent` and no other label. Upstream's docs page for `to-spec` calls the spec's label "an input, not a work order" and suggests removing it after `/to-tickets` has run, so the label marks neither a spec nor a build ticket reliably.

### 2. `to-tickets`' sub-issues and native edges

- **Before** (1.3.1, the "real issue tracker" bullet of step 5): "Use the platform's native blocking / sub-issue relationship where it has one; otherwise set each ticket's "Blocked by" to the blocking issues."
- **After** (1.3.2, line 63): "Use the platform's native blocking relationship where it has one; otherwise set each ticket's "Blocked by" to the blocking issues. If the source was an existing issue, make each ticket its sub-issue (tracker doc's operation)."
- **Before** (the issue template's last section): "A reference to each blocking ticket, or "None (can start immediately)"."
- **After** (line 101): the same, followed by "Omit this section when blockers were set as native edges."
- **Commit and PR:** [cffab50] and [9e2abf8], 2026-10-06, merged as [c07714b], [skills#1188]. The changelog cites [cffab50].
- **In the installed copy:** yes.
- **Nuance for the map.** Three things. Native blocking edges are not new in 1.3.2: the 1.3.1 sentence already asked for them, and named sub-issues only as one way to express them. The sub-issue link is conditional on the source being an existing issue, so tickets cut from a conversation with no spec issue have no parent. And the body still carries a `## Parent` section beside the link, while the body fallback for blockers is a `## Blocked by` section, not wayfinder's `Blocked by:` line at the top. The register's "Ahead of the ceiling" note still holds now that this is released: run against a map, `/to-tickets` would put unlabelled sub-issues under it.
- **Unchanged around it:** "Do NOT close or modify any parent issue"; the local form (`.scratch/<feature-slug>/issues/<NN>-<slug>.md` with bold `**Blocked by:**` and `**Status:**` lines and no parent line); the `ready-for-agent` label.

### 3. `implement`'s ticket reference

- **Before** (1.3.1, the whole body, five one-line paragraphs): "Implement the work described by the user in the spec or tickets." "Use /tdd where possible, at pre-agreed seams." "Run typechecking regularly, single test files regularly, and the full test suite once at the end." "Once done, use /code-review to review the work." "Commit your work to the current branch."
- **After** (1.3.2): a paragraph is added after the first, "If the user passes a ticket reference, fetch it from the issue tracker and state its title before starting. If the reference is ambiguous, ask." The two skill calls are reworded to "Call the Skill tool with "tdd"" and "call the Skill tool with "code-review"".
- **Commit and PR:** the reference in [6d6a5b9], 2026-10-07, [skills#1196]; the Skill tool wording in [e48341a], 2026-10-06, [skills#1189].
- **In the installed copy:** yes, both.
- **Nuance for the map.** The reference is optional ("If the user passes"), and no form is prescribed. How it is fetched is the tracker doc's: on GitHub, "Read it as in **Read an issue** above", which is `gh issue view <number> --json number,title,body,labels,comments`; locally, "Read the file at the referenced path. The user will normally pass the path or the issue number directly." Upstream's docs pages say "passing the issue URL or `owner/repo#2` removes the ambiguity entirely" (`docs/engineering/implement.md`) and that `/implement 03` works on a local tracker (`docs/engineering/to-tickets.md`). So a URL on GitHub and a path locally are both inside the text. The skill still names no assignee, no branch other than "the current branch", no pull request and no close.
