# Which Claude Code version does the Cockpit need?

Research for [#30](https://github.com/dbarjs/hero-synergy/issues/30). Read on 2026-10-06 against the Claude Code changelog (newest entry 2.1.292), the official docs at `code.claude.com/docs`, and the installed CLI (2.1.289, the measured ceiling from [#28](https://github.com/dbarjs/hero-synergy/issues/28)).

Some claims are **measured on old binaries**. I downloaded the linux-arm64 builds of 2.1.139, 2.1.144, 2.1.145, 2.1.161, 2.1.162, 2.1.195, 2.1.196, 2.1.211, 2.1.212, 2.1.231 and 2.1.232 from npm (`@anthropic-ai/claude-code-linux-arm64`). I ran them only with a throwaway `HOME` and `CLAUDE_CONFIG_DIR` in a scratch directory, never against `~/.claude`, and I started no sessions. I ran `agents --help` and `agents --json` against one made-up registry entry (an `interactive` entry with `status: "waiting"` and `waitingFor: "permission prompt"`, for a live dummy process), and I read the bundled JavaScript for the code that writes `status` and `waitingFor`.

## Answer

- **Floor: Claude Code ≥ 2.1.212.** Before 2.1.212, a session waiting on an MCP server's input request, a sandbox-host prompt or a managed-settings prompt shows `busy` in `claude agents --json`, so the Cockpit would show "working" when the session needs you. The changelog entry for 2.1.212 says so, and the status code in the 2.1.211 and 2.1.212 binaries confirms it.
- **Hard minimum: 2.1.162**, the first version whose `claude agents --json` prints `waitingFor`. Without `waitingFor`, the Cockpit can't tell "needs approval" from "waiting for you" (decision 9 in #28). Between 2.1.162 and 2.1.211, only the three prompt kinds above are misreported. Below 2.1.145 there is no `--json` at all.
- **The README floor of ≥ 2.1.139 has to go up.** 2.1.139 was chosen for exec-form hooks, which is still a requirement but no longer the newest one. Since #28, the status model depends on the registry, and the registry needs at least 2.1.162.
- **Tested ceiling: 2.1.289.** #28 measured the interactive registry on that version, and the `--json` output code there produces the same fields as in 2.1.162.

Two later versions improve things the Cockpit can work around, so they don't set the floor. 2.1.196 gives unnamed sessions a default name. 2.1.232 renames the second live session that uses a name to `<name>-<word>-<word>`. See [Not floor-setting](#not-floor-setting).

## Not floor-setting

- **Default display names (2.1.196).** The Cockpit always starts its sessions with `-n "#<number> <title>"` and matches tickets by the `#<number>` prefix. Before 2.1.196, an unnamed, hand-started session has no `name` in `--json`, and it couldn't match a ticket anyway. The only loss is a nicer label wherever the Cockpit lists an unnamed session.
- **Unique names (2.1.232).** Before 2.1.232, two live sessions started with the same `-n` both keep the identical name. Both still match the ticket by prefix, so #21's rule (show both under the ticket with a warning, kill nothing) works the same. `claude --resume "<name>"` with two matching names opens the picker on every version.
- **Backgrounded named sessions listed twice (fixed in 2.1.246).** The [agent view history](https://code.claude.com/docs/en/agent-view#version-history) for v2.1.246 says that before it, "the terminal you pressed `←` in could appear in `claude agents --json` as a second session under the same name". The Cockpit doesn't launch `--bg`, but a developer can press `←` in a Cockpit terminal. On 2.1.212–2.1.245 that shows up as a false duplicate-session warning. It is not a reason to raise the floor further.
- **`claude agents` trust prompt (2.1.225).** It doesn't affect `--json`. **Measured**: 2.1.289 `agents --json` with an empty config, in a folder that was never trusted, with stdin not a TTY, printed `[]` and exited 0.

## Gaps and uncertainty

- **Who writes `status` for interactive sessions before 2.1.212 is read from code, not run.** The 2.1.145, 2.1.162 and 2.1.211 binaries contain the interactive code that computes `status` (`waiting`, then `busy`, then `idle`) and `waitingFor`, and their `--json` printed a made-up entry correctly. I did not start a real interactive session on those versions. Latency and the exact moment of each change (#28's numbers) were measured on 2.1.289 only.
- **Registry entry held back while the trust dialog is open.** #28 measured this on 2.1.289. The changelog doesn't say when registration moved behind trust. Decision 13 in #28 already handles both orders (Cockpit terminal + no `SessionStart` + no entry = starting).
- **When hooks became gated by trust is not dated.** 2.1.3 is an upper bound from a fix that already calls hooks "trust-requiring"; it may be much older. It doesn't matter for a floor at 2.1.212.
- **`SessionEnd.reason` and `SessionStart.source` are not dated separately.** The changelog announces the events (1.0.85, 1.0.62) but not their fields. The only dated change to the values is `"fork"` in 2.1.214, and the Cockpit doesn't use `--fork-session`.
- **When `--plugin-dir` was added is not in the changelog.** Its first mention is a change in 2.1.74. Every version near the floor has it with the one-path-per-flag shape the Cockpit uses (2.1.76).
- **`-n` together with `--resume` (the Cockpit's Resume command).** The [sessions](https://code.claude.com/docs/en/sessions) page says the unique-name rule applies when you "start or resume an interactive session with a name", but no version is given for honouring `-n` on resume. I didn't measure it below 2.1.289.
- **Binaries are linux-arm64.** I read the code shapes on one platform. Claude Code ships one JavaScript bundle per version, so I don't expect other platforms to differ, but I didn't check.
