# Which mattpocock-skills version does the Cockpit read?

Research for [#31](https://github.com/dbarjs/hero-synergy/issues/31), done on 2026-10-07.

Everything below comes from a clone of `mattpocock/skills` (tags `v1.2.3`, `v1.3.0`, `v1.3.1`; `main` at [6fd9479], 2026-10-06), the GitHub release notes for 1.3.0 and 1.3.1, the installed plugin copy at `~/.claude/plugins/cache/claude-plugins-official/mattpocock-skills/1.2.3/` (commit [84fdeff], installed 2026-08-12 per `~/.claude/plugins/installed_plugins.json`), the manifest of `anthropics/claude-plugins-official` and its commit history, and the four resolved tickets this touches ([#10], [#24], [#26], [#29]). "1.2.3" below means the installed commit [84fdeff] unless a tag is named; the wayfinder files are identical at the tag and at that commit ([#10]'s research checked this).

## Answer

**Between 1.2.3 and 1.3.0, exactly one thing the Cockpit parses changed: the Decisions-so-far line.** `- [title](link) — gist` became `- [title](link): gist` ([3216582], 2026-08-19, released in 1.3.0 on 2026-10-04). Every heading, label, claim rule, blocking rule, frontier rule, ticket type and tracker-template operation the scout reads is the same text in 1.3.0 as in 1.2.3, apart from punctuation inside prose. [#10]'s research already lists the new line as D2 ("unreleased"); it is released now.

**What the Cockpit spawns changed in three ways.** The plugin manifest adds `implement-spec`, `pr` and `retro` and drops `resolving-merge-conflicts`; `pr` is the first shipped skill with a nested `metadata:` map in its frontmatter; and six skills' `description` strings are now YAML-quoted (`to-spec` and `setup-matt-pocock-skills` among them). None of the skills a Cockpit Action names (`wayfinder`, `to-spec`, `setup-matt-pocock-skills`, `to-tickets`, `implement`) was added, renamed or removed; the user-invoked set grows from 14 to 16.

**One change outside the Cockpit lands on this repo:** the domain-doc convention is renamed from `CONTEXT.md` to `GLOSSARY.md`. The scout never reads it, but every wayfinder session the Cockpit launches runs `domain-modeling`, which from 1.3.0 looks only for `GLOSSARY.md`.

**The version string does not identify the content.** The official marketplace pins commits of `main`, not tags. Four different contents have shipped under `"version": "1.2.3"`, and two of them ([959a8e9], [c55ee46]) already write the colon line. On 2026-10-07 the marketplace still serves [c55ee46] (pinned 2026-09-22), which reports 1.2.3 and predates the 1.3.0 tag by eleven days; `claude plugin update` today gives a user 1.3.0's wayfinder text labelled 1.2.3. 1.3.1 (2026-10-04) changes nothing the Cockpit reads or spawns.

**Recommendation for the README: no numeric floor for mattpocock-skills.** State "built against mattpocock-skills 1.2.3 to 1.3.1; reads maps written by any release that ships `/wayfinder` (1.1.0 and later)", and keep the Claude Code floor (≥ 2.1.212, [#30]) as the only hard version requirement. Reasons in [Should the README state a minimum skills version?](#should-the-readme-state-a-minimum-skills-version).

### 1. The Decisions-so-far line, in detail

- 1.2.3 template line: `- [<closed ticket title>](link) — <one-line gist of the answer>`. 1.3.0: `- [<closed ticket title>](link): <one-line gist of the answer>`. The HTML comment above it also changed ("the index — one line" → "the index: one line"), which matters only if the scout keeps comments.
- This repo's own map ([#1]) was charted under 1.2.3 and uses the em dash. A map charted under 1.3.0 uses the colon. A map charted under 1.2.3 and worked under 1.3.0 (or under the marketplace's "1.2.3" since 2026-09-16) holds **both forms in one list**, since each session appends its own line. So the parser accepts both per line, never per map, and [#29]'s `map-body-legacy`-style "old form read correctly" is not the right code for an em-dash line: that line is not legacy on a map that is still being written in both forms. Reading either separator as the current form, with no warning, is the cheaper rule; `decision-line-unparsed` stays for lines that match neither.
- The colon form is ambiguous where the em dash was not: a gist can contain `: ` ("Snapshot is tracker-only: sessions join in the Cockpit"). Split at the first `: ` after the closing `)` of the link, not at the last. The em-dash form had the same issue in principle (gists with `—`), so the regex in [#10]'s research (`^- \[(.+?)\]\((.+?)\)\s*(—|:|-)\s*(.*)$`) already does the right thing if the separator group is matched lazily right after the link.
- [#26] decision 7 ("the map's own Decisions-so-far line for the ticket, verbatim") and decision 8 (`decided` = listed under Decisions so far) do not depend on the separator; only the `gist` field extraction does.

### 8. Tracker templates

The three "Wayfinding operations" sections carry the same operations in 1.3.0 as in 1.2.3. GitHub: four lines re-punctuated. GitLab: four. Local: two. All three still say the map holds "the Notes / Decisions-so-far / Fog body", so [#10]'s mismatch 1 is in every release to date, 1.3.1 included. This repo's `docs/agents/issue-tracker.md` is still byte-identical to the 1.2.3 GitHub template; the 1.3.0 template differs from it in four lines of punctuation and no operation.

### 10 to 14. The manifest and frontmatter

At 1.3.0 the 27 manifest skills split 16 user-invoked (`ask-matt`, `grill-with-docs`, `triage`, `improve-codebase-architecture`, `setup-matt-pocock-skills`, `to-spec`, `to-tickets`, `implement`, `implement-spec`, `wayfinder`, `retro`, `grill-me`, `handoff`, `teach`, `to-questionnaire`, `wait-what`) and 11 model-invoked. `resolving-merge-conflicts` had no `disable-model-invocation` line, so its removal does not change the picker. [#24] point 5 already states a new skill "appears with no hero-synergy release"; this is the first release that exercises it.

Frontmatter keys used by any `SKILL.md` under `skills/` at 1.3.0: `name` (37), `description` (37), `disable-model-invocation` (22), `argument-hint` (4, unchanged from 1.2.3: `handoff`, `teach` and two unpromoted skills), `metadata` (1, new). Claude Code's skills doc lists `metadata` as "Free-form YAML map for your own key-value data … Claude Code doesn't act on its contents, and drops a value that isn't a map", and says Claude Code ignores unknown fields; so the Cockpit's reader should ignore unknown keys too, and must parse a nested map without failing.

### 18. `CONTEXT.md` → `GLOSSARY.md`

The 1.3.0 `setup-matt-pocock-skills` explores for `GLOSSARY.md` and writes a `domain.md` that names `GLOSSARY.md`; `domain-modeling`, `grill-with-docs`, `triage`, `tdd`, `diagnosing-bugs`, `ask-matt`, `codebase-design`, `wait-what` and `pr` were all changed in the same PR. A wayfinder session on 1.3.0 that resolves a grilling ticket calls `domain-modeling`, which reads and writes `GLOSSARY.md`; with this repo as it is, it finds no `GLOSSARY.md`, proceeds silently (the `domain.md` rule) and would create a second glossary beside `CONTEXT.md`. The scout, the snapshot and the Cockpit never read either file, so no decision in [#24], [#26], [#29] or [#10] moves. The repo action, when the installed plugin is upgraded past [c55ee46]: `git mv CONTEXT.md GLOSSARY.md` and update `CLAUDE.md` ("### Domain docs" and "Writing to `main`"), `docs/agents/domain.md` (or re-run setup) and the one sentence in ADR 0003, in a single commit, so a session on either version finds exactly one glossary. Until then, sessions keep running the installed 1.2.3, which reads `CONTEXT.md`.

## The version string does not identify the content

- `anthropics/claude-plugins-official` pins `mattpocock-skills` to a commit (`source.sha`), bumped by a nightly workflow or by hand, with no relation to upstream tags. Observed pins: [84fdeff] on 2026-08-12 (this machine's install), [3cca18b] before 2026-09-16 (the earliest manifest commit read), [959a8e9] from 2026-09-16 (`bump(mattpocock-skills): 3cca18b3 → 959a8e9f`, #6173), [c55ee46] from 2026-09-22 ("Manual SHA bumps batch B2", #6283) and unchanged through the manifest's latest commit on 2026-10-05.
- All four report `"version": "1.2.3"`. [959a8e9] and [c55ee46] contain [3216582], so they write the colon line, and [c55ee46]'s wayfinder, template, `to-spec`, `to-tickets`, `research`, `prototype` and `grilling` files are byte-identical to 1.3.0's; what it lacks of 1.3.0 is the GLOSSARY rename in `setup-matt-pocock-skills/SKILL.md` and `domain.md`, and the manifest changes (verified with `git diff c55ee46 v1.3.0` on those paths: three files, all in that set).
- `claude plugin list --json` reports `version` only (`1.2.3` here, [#24]'s source for the QuickPick description). The commit is in `~/.claude/plugins/installed_plugins.json` as `gitCommitSha`, which [#24] point 2 chose not to parse.
- The skills.sh route "writes the skills into your repo as ordinary files you own" that update only on `npx skills update` (upstream `README.md`), so a project's copy is whatever the repo held on the day it was copied, with no version string of its own.

Consequence: "which version wrote this map" cannot be answered from any version number, and "which version is installed" cannot be answered precisely from `claude plugin list`. The Cockpit's reading rules have to cover every form a shipped `main` has written, which is what [#10] and [#26] already assume.

## Should the README state a minimum skills version?

No numeric floor. The Claude Code floor ([#30], ≥ 2.1.212) exists because the Cockpit depends on a binary's behaviour at runtime and can refuse to work below it. The plugin is different on three counts:

1. **Nothing the Cockpit reads is gated by a version.** Maps outlive the plugin that wrote them, and the Cockpit reads both decision-line forms regardless of what is installed today. The only plugin-dependent capability is "is `/wayfinder` installed", which [#24] point 7 already reports as a health row ("no `wayfinder`, Work ticket unavailable").
2. **The number is not checkable.** `claude plugin list --json` says 1.2.3 for four different contents, and the official marketplace serves "1.2.3" with 1.3.0's text three days after 1.3.1 was tagged. A README line "≥ 1.3.0" would be false for users on the current marketplace pin and unenforceable by the Cockpit.
3. **Every release that ships `/wayfinder` is readable.** `wayfinder` entered the plugin in v1.1.0 (2026-07-08, [#10] M5/D1) with the five headings the Cockpit expects; the user-invoked skills the Actions name (`wayfinder`, `to-spec`, `to-tickets`, `implement`, `setup-matt-pocock-skills`) are in every manifest from 1.1.0 to 1.3.1.

What to state instead, in the Requirements section [#17] put in `packages/vscode/README.md` (not yet written): "mattpocock-skills with the `wayfinder` skill (any release from 1.1.0; built and tested against 1.2.3 and 1.3.1), installed as a plugin or with skills.sh." If Eduardo wants a number anyway, the defensible one is **≥ 1.1.0** (first release with `/wayfinder`), stated as "any release that ships `/wayfinder`", never 1.3.0.

## After 1.3.1 (unreleased)

On `main` at [6fd9479] (2026-10-06), four changesets wait. Two touch things the Cockpit reads:

- **`to-tickets` makes each ticket a sub-issue of its source issue** and omits `## Blocked by` when blockers are native edges; the GitHub template gains "Make an issue a sub-issue of a parent" (`gh issue create --parent <parent>`, `gh issue edit <parent> --add-sub-issue <child>`, `gh` 2.94+; `gh api … /sub_issues` for older `gh`; `Part of #<parent>` without sub-issues). Changeset `.changeset/to-tickets-sub-issues.md`. Effect on the Cockpit: none while `/to-tickets` is given a spec issue, which [#24] point 3 assumes. If a user runs `/to-tickets <map-url>` against a map, the implementation tickets become sub-issues of the map with no `wayfinder:` label, and the scout reports each as `type-missing` (loud, [#29]). That is the correct reading: they are not decision tickets.
- **GitHub template's external-PR listing** switches from `gh pr list … authorAssociation` to `gh api --paginate 'repos/{owner}/{repo}/pulls?state=open'`. Changeset `.changeset/github-tracker-external-pr-list.md`. Triage only; the scout never reads PRs.

The other two (`implement` says "call the Skill tool with tdd/code-review"; `handoff` names the temp dir) change nothing the Cockpit reads or spawns. Both tracker-template changesets tell users to "re-run `/setup-matt-pocock-skills` to refresh `docs/agents/issue-tracker.md`"; that would overwrite this repo's doc, which also holds the unchanged wayfinding section.

## What could not be verified

- **The marketplace pin before 2026-09-10.** Only commits since that date were read; [84fdeff] as the pin on 2026-08-12 comes from this machine's `installed_plugins.json`, not from the marketplace history.
- **Whether `claude plugin update` on this machine would fetch [c55ee46].** Not run, to keep the installed 1.2.3 reference intact. The claim rests on the manifest's current `source.sha`.
- **How Claude Code's `/` menu renders `pr`'s `metadata` block.** Read from the skills doc only; not exercised.
- **What skills.sh (`npx skills add mattpocock/skills`) installs today.** Not run. What it copies comes from the plugin's README (files you own, updated on `npx skills update`) and the 1.3.0 changelog entry for PR #911 (it reads each `SKILL.md`'s frontmatter and skipped six skills while their YAML was invalid); which git ref it reads was not checked.
- **Whether any real map holds both decision-line forms.** This repo's map has only em-dash lines; the mixed case is inferred from the append-one-line rule in `SKILL.md`, not observed.
